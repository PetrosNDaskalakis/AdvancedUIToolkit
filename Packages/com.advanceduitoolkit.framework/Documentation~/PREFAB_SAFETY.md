# Advanced UI Toolkit v0.9.4 — Prefab Safety & Validation

This is a **backward-compatible Editor stabilization release**. Existing generated C# API names, `UIView<T>`, `UIEventScope`, serialized UIBindingRoot fields, and style profiles do not change.

## Recommended workflow

1. For a scene-only UI object, select the top-level UI root in **Tools → Advanced UI Toolkit → Binder → Bindings**.
2. For a prefab asset or variant, **open that prefab in Prefab Mode**, select its editable outermost UI root, and scan there.
3. Run **Scan & Preview Changes**, then review errors and warnings.
4. Fix missing components and duplicate names; review removals or deliberate public API renames.
5. Select **Save Manifest + Generate C#**, then **save your scene or prefab**.
6. Use **Diagnostics** to inspect currently open scenes and prefab assets. The tool does **not** validate unopened scene files.

## Nested prefab behavior

- A nested control group that has its own `UIBindingRoot` forms a **separate binding scope**. The parent screen does not generate accessors for its children.
- A nested prefab without its own `UIBindingRoot` can contribute controls to the parent screen. Advanced UI Toolkit warns about this situation, since structural changes to that prefab can invalidate parent references.
- The manifest checker detects component references that cross an independent binding boundary.
- Direct generation on scene prefab **instances** is blocked: open the source prefab in Prefab Mode. This avoids accidental instance overrides. Prefab variants should be edited by opening the variant itself.

## Safer code generation

- A UI root cannot silently overwrite an existing `.cs` output unless its saved generation profile owns that path.
- A second UI root cannot claim another root's configured generated output. Sources of the **same prefab root instance** are considered one logical owner; distinct UI roots in one prefab are not.
- Changing a class name or output folder requires manually moving or removing the previous generated file first, to avoid duplicate C# classes.
- Generated files still require the `// <auto-generated />` header; user-authored C# files are not overwritten.
- The generator writes to a temporary file before replacing the generated source. If the source write fails, the binding manifest is not modified. The scene or prefab still needs to be saved after successful generation.
- Breaking changes (removals and public-property renames) still require confirmation, and automatic generation will not accept them.

## Limitations

- Prefab asset and currently opened-scene output-owner discovery occurs when generating. On very large projects it may add a noticeable delay; this check is intentionally not done on every `Get<T>` call.
- Editor code compilation and tests must be verified in the installed Unity version. This release has not been compiled by Unity as part of package creation.
- Moving a prefab control into a different independently bound root is a breaking scope change and should be reviewed rather than auto-applied.
- File staging safeguards are not a transactional undo system for both generated C# and serialized Unity scene changes. Keep project files in version control.

## Suggested manual regression tests

1. Verify a normal scene UI panel generates its existing bindings unchanged.
2. Add a nested prefab with its own `UIBindingRoot`. Confirm its children are excluded from the parent binding scan.
3. Add a nested prefab without a `UIBindingRoot`, containing a named Button. Confirm the warning appears.
4. Delete a saved button reference. Confirm Diagnostics reports it and Automation requires manual review.
5. Create two independent UI roots with the same generated class output. Confirm the second root cannot overwrite the first.
6. Open a source prefab in Prefab Mode and verify binding generation works. In a scene, try to generate directly on one of its instances and confirm it is blocked.
7. Run the Editor regression tests, then repeat the `WeaponPanel` PlayMode and enable/disable tests.
